# План работ

Подход: не писать эмуляцию SA-1110 с нуля (она уже есть в QEMU как
`hw/arm/strongarm.c`), а написать board-файл для Jornada 720 по образцу
`hw/arm/collie.c`, постепенно добавляя периферию.

## 1. Минимальный скелет машины

- [x] Завести `hw/arm/jornada720.c`: создание CPU (SA1110-совместимое ARM-ядро),

  `-M jornada720 -nographic` стартует и не падает даже без ROM-образа.
- [x] Замаппить реальный ROM-образ и посмотреть, что происходит.

  реального ROM". Текущая точка зависания: бесконечный poll на
  SA-1111 (`0x40000810`).
- [x] Критерий готовности **скорректирован дважды**: сначала выяснилось,
  что до UART ещё далеко (сначала SA-1111), потом — что после SA-1111
  идёт ещё и Epson-контроллер дисплея. UART по-прежнему молчит, но это

## 1.5. SA-1111 — минимально достаточная модель ✅ (частично)

- [x] Точные базы блоков SA-1111 добыты не из даташита (bitsavers-копия
  битая), а из реальных исходников Linux (`arch/arm/include/asm/hardware/
  sa1111.h` + `arch/arm/common/sa1111.c`, через jsdelivr — GitHub напрямую
  заблокирован сетью телефона). SSP-база оказалась `0x0800` (не угадывалась
  из упрощённого заголовка), PCMCIA — `0x1800`. Подробности и то, как
  опровергли гипотезу "это USB" — в `docs/research.md`.
- [x] Реализован узкий `MemoryRegion` с кастомными `ops` поверх SSP-диапазона
  (`0x40000800`, 4 КиБ), возвращающий фиксированные "статус"-биты по
  аналогии с on-chip `strongarm_ssp` (`TNF|RNE|TFS|RFS`, без "busy"/"overrun").
  **Экспериментально, не подтверждено по настоящему даташиту SA-1111**
  (глава 8, Table 8-8 — так и не достали читаемую копию).
- [x] Критерий готовности выполнен: poll на `0x810` больше не висит,
  код идёт дальше — прямиком в инициализацию Epson-контроллера (см. 1.6).
- [ ] Осталось при желании: найти рабочую копию даташита SA-1111 (глава 8)
  и заменить догадку про биты SSP на подтверждённые значения — на случай
  если где-то дальше эта же заглушка всё-таки даст сбой на другом бите.

## 1.6. Epson-контроллер дисплея — новый стопор

После SA-1111 код полностью обнуляет весь Epson framebuffer (все 512 КиБ)
и пишет `0x01` в регистр `0x1fc` (1 байт) — и виснет сразу после этого,
детерминированно, на том же месте при повторных запусках. Serial-консоль
всё ещё молчит.

- [x] Разобраться с зависанием после `0x1fc` — оказалось, это была НЕ
  проблема Epson, а баг в позициях битов `SSSR` (SSP Status Register) в
  `hw/arm/strongarm.c`: скопированы из PXA25x, сдвинуты на 1 бит
  относительно настоящего SA-1110 (подтверждено официальным SA-1110
  Developer's Manual, bitsavers.org — в отличие от SA-1111-мануала, этот
  оказался нормальным PDF). Исправлено (`patches/0003-...`). Подробный
  разбор — `docs/research.md`.
- [x] Критерий выполнен куда лучше, чем ожидалось: после фикса код не
  просто "идёт дальше", а реально **рисует во framebuffer** (запись
  `0xFFFF` = белый цвет, 16 бит/пиксель, широкий диапазон адресов —
  похоже на сплэш-экран/фон UI).
- [ ] Модель конкретного Epson-чипа (SED13xx?) и семантика регистра
  `0x1fc` — так и остались не выясненными, но перестали быть блокером:
  наша грубая unimplemented-заглушка для Epson оказалась достаточной,
  чтобы пройти этот этап. Actual экран увидим только на шаге 2, когда
  будет написан настоящий LCD/Epson-девайс с реальным framebuffer.

## 1.7. Новый стопор: Data Abort после релокации кода в RAM

После отрисовки во framebuffer код проваливается в **настоящий Data
Abort** (`PC=0xffff0010` — вектор Data Abort в высокой таблице векторов,
`0xFFFF0000`, т.е. V-бит CP15 уже включён; CPU-режим `abt32`).
`LR_abt=0x800558cc` — это уже не адрес во флеше, а что-то в районе
on-chip peripheral-пространства/RAM: к этому моменту **код релоцировал
себя в RAM** и исполняется оттуда. Из-за этого прежний приём (дизассемблировать
статический файл ROM через `objdump`) больше не работает напрямую —
нужно читать содержимое RAM самой запущенной VM в момент зависания
(через gdbstub QEMU: `-s -S` + `gdb -ex "target remote :1234"`, а не
статический файл).

- [x] Подключиться через QEMU gdbstub, а не статический `objdump`, чтобы
  прочитать код прямо из памяти VM в момент абort'а.
- [x] Понять причину: это оказался не Data Abort, а **Prefetch Abort**
  (Data Abort был вторичным следствием). Точная причина найдена —
  см. `docs/research.md`, раздел "Найдена настоящая первопричина:
  MMU-enable без "зазора" в QEMU". Коротко: ROM включает MMU (`mcr
  SCTLR`) и следующей же инструкцией переходит на высокий виртуальный
  алиас кода (`0x80000000+`) — классическая ARM-идиома, полагающаяся на
  то, что "следующая инструкция после enable ещё выполняется по старому
  отображению". QEMU это не воспроизводит (новое состояние MMU
  применяется немедленно), а низкий алиас (откуда физически идёт
  исполнение) в таблице страниц не замаплен вовсе — отсюда мгновенный
  Prefetch Abort ещё до перехода на высокий алиас.
- [x] Критерий готовности выполнен: это баг/пробел эмуляции (в общем
  ARM CPU core QEMU, `target/arm`, а не в нашей плате), не легитимное
  поведение прошивки.
- [x] Изучили `target/arm/helper.c`/`translate.c` — нашли готовый флаг
  `ARM_CP_SUPPRESS_TB_END`, добавили его на запись SCTLR только для
  `ARM_FEATURE_STRONGARM` (sa1100/sa1110 — только `collie` и наша
  машина). Дало нужную "отсрочку на одну инструкцию". Не проверено на
  регрессии для `collie`. См. `docs/research.md`.
- [x] Нашли и пофиксили второй стопор после этого: SA-1110 Power
  Manager (`0x90020000`, регистр POSR на `+0x1c`) вообще не
  реализован в `strongarm.c` — ROM ждёт бит "oscillator stable",
  который никогда не появлялся. Добавлен узкий стаб в
  `jornada720.c` (тот же паттерн, что SA-1111 SSP). См.
  `docs/research.md`.
- [x] Третий стопор (Data Abort на записи в `0xffff5070`) — оказался
  вторичным. Настоящая причина: QEMU делает UNDEF из инструкций с
  NV-условием на ARMv4, а на StrongARM это NOP, и обработчик Prefetch
  Abort в WinCE на это полагается. Исправлено (`patches/0005-...`). После
  фикса CE работает дальше: пользовательские процессы, подкачка страниц,
  IRQ. См. `docs/research.md`, раздел "Третий стопор решён".
- [ ] Проверить все правки `target/arm` (0002, 0004, 0005) на регрессии
  для `collie`.

## 2. Экран

**Пересмотрено после разбора strongarm.c (см. docs/research.md):**
LCD-контроллера SA-1110 в QEMU **нет вообще** (ни в strongarm.c, ни в
collie.c). Это не мелкая доработка "передать конфиг панели", а отдельное
устройство, которое нужно писать с нуля — по сути ещё один шаг размером
с 1.

- [x] Первый шаг: Epson-framebuffer (`0x48200000`, 512 КиБ) — обычная
  RAM, выводится как фиксированная панель 640x240 RGB565. Итог: на экране
  лого **HP invent** (`docs/img/first-boot-logo.png`). LCD-контроллер самого
  SA-1110 для этого не понадобился: на Jornada 720 экран на Epson.
- [x] Кадр застывал на лого: `explorer.exe` ждал конца анимации по
  `GetTickCount`, а время ядра улетало из-за ISR таймера, который в QEMU
  без icount повторно входит раньше совпадения. Лечится запуском с
  `-icount shift=3,align=off`. После этого видны элементы рабочего стола
  (`docs/img/desktop-icount.png`). См. `docs/research.md`, продолжение 7.
- [x] CE висел в `ddi.dll` на опросе FIFO BitBLT: драйвер рисует всё через
  2D-движок Epson S1D13806. Движок реализован в `jornada720.c`
  (16 bpp; move с цветовым расширением, линейная адресация и 8 bpp — нет).
- [x] Критерий готовности выполнен: рабочий стол Windows CE
  (`docs/img/desktop.png`), система в idle.
- [ ] Декодировать регистры дисплея Epson (start address, stride, bpp),
  если CE их поменяет; сверить семантику BitBLT с даташитом S1D13806.
- [ ] «Unidentified PCCard Adapter» — PCMCIA SA-1111 отвечает мусором;
  «Backup Battery Very Low» — статус батареи. Не блокирует.
- [ ] Узнать, можно ли обойтись без `-icount` (или взять `shift=auto`):
  сейчас эмуляция медленная.

- [x] Устройство: MCU на встроенном SSP SA-1110 (а не SA-1111), протокол

- [x] Модель MCU `j720-mcu`: клавиатура (из событий клавиатуры QEMU) и
  тачскрин (абсолютная мышь / QMP), импульсы GPIO9 на каждый отсчёт.
- [x] Заглушка UDC SA-1110: без неё `udcser.dll` съедал CPU.
- [x] Критерий выполнен: Enter/Esc закрывают диалоги, штатная калибровка
  пройдена, тапы попадают точно (`docs/img/touch-calibrated.png`).
- [x] На телефоне (SDL, на весь экран, палец) калибровка шла по кругу.
  Лог `J720_TOUCH_DEBUG` показал: маппинг верный, систематического сдвига
  нет, промахи ±6–12 px в разные стороны — точность пальца; со второй
  попытки CE калибровку принял. Для отладки есть пункт sxmo
  «Jornada 720: touch debug» (лог в `~/touch.log`).
- [x] Калибровка (и вообще всё) терялась при перезапуске: CE держит
  реестр и файлы в RAM (на настоящем устройстве она на батарейке), флеш
  не пишет. Теперь `run.sh` усыпляет машину в файл при выходе и
  восстанавливает при запуске (~1 с вместо ~30 с загрузки):
  `-action shutdown=pause` + `j720-save.py` (QMP `migrate` в
  `~/.local/state/qemu-jornada720/j720.state`). Для этого у MCU, Epson и
  UDC появились `vmsd`; закрытие SDL-окна больше не форсирует poweroff
  (`patches/0010`). Сигнал самому QEMU всегда означает выход без
  сохранения, поэтому пункт «stop» шлёт SIGTERM помощнику. `--fresh` /
  пункт «cold boot» — холодная загрузка; не загрузившееся сохранение
  уезжает в `j720.state.bad`.
- [x] После восстановления всё тормозило (касание — 4–10 с): шквал
  прерываний от будильника RTC, два бага в `strongarm.c`, см.
  `patches/0011`. После фикса ~100 IRQ/с, отклик 0,2–0,5 с, будильник
  CE срабатывает вовремя. (Вывод «часы CE в быстром режиме идут 1:1» из того же замера был
  неверен: часы на панели задач берутся из RTC, а он идёт по хосту.)
- [x] Время в CE: тик CE (`GetTickCount`, таймеры, таймер Солитера)
  идёт по виртуальному времени QEMU; при `shift=6` замер по OS-таймеру
  SA-1110 — 16x быстрее реального. `run.sh` теперь по умолчанию
  `shift=auto` (1.00x через ~20 с после старта, отклик 0,14–0,35 с);
  быстрый режим — `--fast`. Часы на панели задач — из RTC, он и так
  идёт по хосту, в том числе после восстановления.
- [x] Клавиши дублировались. Автоповтор CE считает время по своим
  часам, а под `-icount` они спешат: в быстром режиме нажатие на 50 мс
  давало «aa», 400 мс — 8 букв; даже в `--realtime` 100 мс давали «bb».
  Теперь MCU отдаёт обычную клавишу как мгновенное make+break на каждое
  key-down хоста, автоповтор берётся от хоста (sway), модификаторы
  держатся честно. Правые Ctrl/Alt сопоставлены левым (у клавиатуры
  пользователя Alt — это RightAlt, до CE он не доходил). Ctrl+Alt+Q
  сначала отпускает все клавиши в госте, иначе после восстановления CE
  считал Ctrl+Alt зажатыми и буквы не печатались.
- [ ] Проверить Ctrl+Alt+Q → сохранение на настоящей клавиатуре
  (закрытие окна и «stop» проверены; `wtype` хоткей не доставляет).
- [x] Батарея (GETBATTERYDATA): формат и пороги из `battdrv.dll`,

- [ ] Удобный запуск для человека: VNC (`-vnc :0`), в сборке есть.

## 4. Второстепенная периферия (по необходимости)

- [x] Сеть. У Jornada 720 нет встроенной сети; в ROM есть NE2000.DLL и
  детектор `DetectNE2000` для PC Card. Сделаны контроллер прерываний и
  PCMCIA-интерфейс SA-1111 (регистры по Linux `sa1111.c`,
  `sa1111_generic.c`) и NE2000-карта в слоте 0: CIS (FUNCID network,
  FUNCE с MAC, CONFIG 0x3f8, CFTABLE 0x300-0x31f + IRQ), COR/CCSR,
  I/O-окно на ядро `hw/net/ne2000.c`, nIREQ → READY слота → IRQ 49
  SA-1111 → GPIO1 SA-1110. Бэкенд — `-nic user` (slirp), сборка требует
  libslirp-dev. Проверено: CE находит карту («NE2000 Compatible Ethernet
  Driver»), DHCP даёт 10.0.2.15, Pocket IE открывает http://example.com/,
  сеть работает и после восстановления из сохранения. «Unidentified
  PCCard Adapter» больше нет. Грабля: вложенный dispatch в регион
  NE2000 того же устройства блокировался защитой от re-entrant I/O
  (чтения давали 0) — `disable_reentrancy_guard`.
- [x] HTTPS в Pocket IE не работает (старый TLS). Обход: локальный
  FrogFind (`frogfind-setup.sh`, код вне репозитория в
  `~/.local/share/qemu-jornada720/frogfind`), `run.sh` поднимает
  `php -S 127.0.0.1:8720` на время работы эмулятора, в CE —
  `http://10.0.2.2:8720/`. Публичный frogfind.com лежит: DuckDuckGo
  отвечает анти-бот страницей на запросы без User-Agent; локально PHP
  шлёт браузерный UA (`-d user_agent`). Проверено в Pocket IE: поиск и
  HTTPS-статья через `read.php`.
- [x] Передача файлов в CE: `j720-router.php` отдаёт `~/jornada-files` на
  `/files/` того же сервера. Проверено: `.cab` скачивается через диалог
  «File Download» (по умолчанию в `\windows`). `.txt` IE открывает прямо в
  окне и читает UTF-8 как cp1252. Обратно (из CE на хост) пока никак.
- [ ] Русский ввод: в ROM раскладки нет; кириллица отображается (шрифт
  ROM, Unicode). Кандидат — RPK Russian Phonetic Keyboard 1.2 с
  HPC:Factor (freeware, нужна учётка), совместимость с H/PC 2000 ARM не
  проверена.

- [ ] IrDA, звук, подсветка, батарея/питание — по мере того, что реально
  требуется для стабильной работы CE (не факт, что всё это нужно сразу).
