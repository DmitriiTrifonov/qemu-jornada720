# Research / собранные факты

## Железо HP Jornada 720/728

- CPU: **Intel StrongARM SA-1110**, 206 МГц (не SH3 — SH3 стоит в других
  линейках Jornada, например 680/690 и 520/540).
- ОС: Windows CE (Handheld PC 2000, на 720/728).
- Подробная распиновка/карта регистров: см. hardware config doc
  (jornada720.txt, из архива уровня "hpc factor" / университетских зеркал) —
  описывает маппинг SA1110 serial port, GPIO, control registers и т.п.
  Это и есть основа для memory map будущей QEMU-машины.

## Прецедент в MAME

- Файл `src/mame/**/jornada.cpp` — драйвер именно HP Jornada 720/728.
- Использует отдельный, переиспользуемый файл эмуляции чипа `sa1110.cpp`
  (аналог `hw/arm/strongarm.c` в QEMU).
- Автор основной работы — **Ryan Holtz**.
- Результат: Windows CE грузится "до узнаваемого состояния" (виден UI).
- Известные проблемы:
  - нужно запускать с флагом `-debug` и вручную подкручивать скорость CPU
    через cheat-параметры отладчика, иначе не бутится нормально;
  - тачскрин работает нестабильно/криво;
  - даже на десктопном **Intel i5-4670K** эмуляция описывается как
    "очень медленная", загрузка до рабочего стола — "целая вечность".
- PR с доработкой клавиатурной раскладки смержен в mamedev/mame в январе 2024 —
  то есть проект живой, но статус экспериментальный, не production-ready.
- Значение для нас: подтверждает, что задача **решаема** (SA-1110 достаточно
  эмулируется программно, чтобы Windows CE стартовала), и даёт готовый
  referencing-таргет — можно сверяться с логикой jornada.cpp/sa1110.cpp при
  написании аналога под QEMU.

## Состояние в QEMU

- Готовой машины для Jornada (ни 56x/SA-1110, ни 6xx/7xx на SH3) в апстриме нет.
- Поиск по GitHub / qemu-devel / mail-archive не дал патчей или форков с
  поддержкой Jornada — похоже, что до сих пор никто не выкладывал такую работу
  в открытом виде.
- **`hw/arm/strongarm.c`** (+ `strongarm.h`) — эмуляция чипа SA-1110, но
  она **неполная** (см. разбор ниже) — не стоит переоценивать, сколько
  "готового" там есть.
- Её использует машина **`hw/arm/collie.c`** — Sharp Zaurus SL-5500,
  тоже построен на SA-1110. Основной шаблон/референс для платы.

### Разбор `hw/arm/strongarm.c` — что реально уже есть (128 KiB, 1671 строка)

`sa1110_init()` (главная точка входа, `strongarm.h`) поднимает:

| Периферия | Адрес      | Реализация |
|---|---|---|
| PIC (контроллер прерываний) | `0x90050000` | `strongarm_pic` |
| OS-таймер | `0x90000000` | переиспользован `pxa25x-timer` (не своя модель!) |
| RTC | `0x90010000` | `strongarm-rtc` |
| GPIO | `0x90040000` | `strongarm-gpio` |
| PPC (Peripheral Pin Controller) | `0x90060000` | `strongarm-ppc` |
| UART x3 | `0x80010000` / `0x80030000` / `0x80050000` | `strongarm-uart` |
| SSP (синхронный serial/SPI, обычно touchscreen ADC / кодек) | `0x80070000` | `strongarm-ssp`, с выведенной наружу SSI-шиной |

**Чего в strongarm.c НЕТ** (моя более ранняя запись в этом файле была
неточной — ошибочно предполагала, что LCD/DMA/PCMCIA уже есть):

- **LCD-контроллер — отсутствует полностью.** У SA-1110 в реальности есть
  встроенный LCD-контроллер, но в QEMU его никто не реализовал. Машина
  `collie` тоже не подключает никакого экрана — то есть на сегодня в QEMU
  **нет вообще ни одной SA-1110-платы с рабочим видеовыходом**.
- DMA-контроллер — не реализован как устройство (хотя в PIC заведены
  IRQ-линии `SA_PIC_DMA_CH0..5` под него — заготовка есть, самого блока нет).
- PCMCIA-контроллер — тоже не часть strongarm.c. У `collie` вместо этого
  подключен Sharp-специфичный `scoop` (0x40800000) — то есть это
  Zaurus-специфика, для Jornada неприменимо один в один.
- Флеш подключается на уровне платы (`collie.c`), не чипа — это ожидаемо
  и одинаково для любой SA-1110 платы, в т.ч. будущей Jornada.

**Вывод (скорректированный):** писать модель CPU-ядра и базовых
блоков (PIC/таймер/RTC/GPIO/UART/SSP) с нуля не требуется — это есть и
переиспользуется 1:1, адреса общие для любого SA-1110-чипа, в т.ч. Jornada 720.
Но **экран — не "мелкая доработка", а отдельная, довольно большая
задача**: LCD-контроллер SA-1110 в QEMU нужно писать с нуля (в MAME он,
судя по всему, есть — раз там видно UI — значит это одна из вещей, которую
стоит внимательно сверить по их `sa1110.cpp`, а не только по железным
даташитам).

Отсюда практический вывод для плана: реалистичная первая цель — это
именно **шаг 1 (загрузка до UART-консоли, без экрана)**, он полностью
укладывается в то, что уже есть в strongarm.c. Шаг 2 (экран) по объёму
работы сопоставим с написанием ещё одного устройства с нуля, а не с
"передать конфиг панели в готовый контроллер", как было наивно записано
здесь раньше.

## Карта памяти Jornada 720 (из hardware config doc, jornada720.txt)

| Регион | Адрес | Размер | Статус в нашей машине |
|---|---|---|---|
| System Flash/ROM | `0x00000000` | 32 MiB | подключен (`SA_CS0`, `pflash_cfi01`) |
| Boot Flash/ROM (только debug-плата) | `0x10000000` | 1 MiB | не нужен, это для отладочной платы, не для обычного устройства |
| SA-1111 companion chip | `0x40000000` | — | НЕ эмулируется, совпадает с `SA_CS4` |
| Epson-контроллер дисплея | `0x48000000` | — | НЕ эмулируется |
| Epson frame buffer | `0x48200000` | 512 KiB | НЕ эмулируется |
| System SDRAM | `0xC0000000` | 32 MiB | подключен (`SA_SDCS0`) |

Важное уточнение по экрану: у Jornada 720 дисплей выведен не через
встроенный в SA-1110 LCD-контроллер, а через **отдельный Epson-чип**
(похоже на семейство Epson SED13xx — точная модель ещё не подтверждена).
Проверил исходники QEMU (`grep -rli` по `hw/` и `include/`) — **ни SA-1111,
ни какого-либо Epson SED13xx контроллера в QEMU нет вообще**. Значит шаг
"экран" требует написания не одного, а потенциально **двух** устройств
(SA-1111 — если он нужен раньше экрана, например для клавиатуры/USB;
Epson-контроллер — для самого видео). Нужно уточнить по MAME `sa1110.cpp`/
`jornada.cpp`, что из этого они реализовали и в каком объёме.

## Прогон реального ROM (2026-09-28)

Пользователь поднял у себя дома веб-сервер и передал реальные дампы с
Jornada 720: `jornada720.bin` (ровно 32 МиБ — точно system flash) и
`jorn720_eeprom.bin` (256 байт, пока не использован). Файлы лежат в
`roms/` (не в git, см. `.gitignore`).

Загрузка (`-drive if=pflash,format=raw,file=roms/jornada720.bin`) сразу
показала: **тишина в serial-консоли** — так что пришлось отлаживаться
через `-d in_asm`/`-d unimp`/`-d guest_errors` и временную инверсию
`mc->ignore_memory_transaction_failures`, чтобы понять, где именно
исполнение застревает. Разбор по шагам:

1. **Сброс → `0x00000000` → branch на `0x00001000`** — стандартный
   ARM-паттерн (короткий вектор сброса прыгает на реальный код). ОК.
2. С `0x1000` до `~0x107c` код несколько раз пишет в **`cp15, c1, c1, opc2=0`**
   (не крн=15 "impdef", а именно `c1,c1`) — QEMU логировал это как
   `unsupported AArch32 system register` и **бросал Undefined Instruction**.
   На реальном железе это легитимный (хоть и слабо документированный)
   SA-1110-специфичный "Auxiliary Control Register", который просто должен
   тихо срабатывать. Так как вектор Undefined Instruction (`0x00000004`)
   в этом ROM пуст (`0xFFFFFFFF`), исключение зацикливалось само на себя —
   полное зависание уже на первых ~30 инструкциях.
   **Фикс:** добавил RAZ/WI-запись в `strongarm_cp_reginfo`
   (`target/arm/helper.c`, по аналогии с уже существующим `C9_READBUFFER`) —
   см. `patches/0002-sa1110-aux-control-register-dummy.patch`.
3. После фикса исполнение уходит гораздо дальше (`0x4f7xx`-`0x505xx`),
   делает что-то похожее на калиброванный **delay-loop** через запись
   нарастающего счётчика в регистр отладочной платы (CL-CD1284,
   `0x1a000400`) — это ожидаемо и не мешает (на реальном железе без
   debug-платы это обращение просто читает "мусор" с шины, а не падает;
   поэтому `ignore_memory_transaction_failures` должен остаться `true`,
   как у `collie.c` — я на секунду включал `false` только для диагностики
   через Data Abort, там и увидел `DFAR 0x1a000400`, что и навело на след).
4. Дальше код инициализирует **SA-1111** (пишет в блоки по смещениям
   `0x0000`, `0x0004`, `0x1000-0x102c`, `0x1608-0x1620` — похоже на
   System Bus Interface / PCMCIA / GPIO блоки) и в итоге **зависает
   намертво в бесконечном read-poll по смещению `0x000810`** от базы
   SA-1111 (`0x40000810`). Заглушка (`create_unimplemented_device`)
   всегда отдаёт 0, а код явно ждёт другого значения бита — реальный
   SA-1111 в этот момент отвечает чем-то, что делает проверку истинной.
   За 15 секунд — больше 2 млн одинаковых чтений одного и того же адреса.

Добавлены read/write-заглушки (`hw/misc/unimp.h` →
`create_unimplemented_device`) на все ещё не эмулированные регионы —
SA-1111 (`0x40000000`), debug-плата (`0x1a000000`), Epson-регистры
(`0x48000000`) и Epson-framebuffer (`0x48200000`) — чтобы дальнейшие
обращения были видны через `-d unimp`, а не тонули в тишине.

## Раскопка даташита SA-1111 и разгон стопора на `0x810` (2026-09-28, продолжение)

**Проблемы с источниками:**
- Полный "Developer's Manual" (278242-002) на bitsavers.org оказался
  **битым** — под этим именем лежит старая dead-link HTML-страница
  Intel (~2000 год), просто сохранённая с расширением `.pdf` и
  `Content-Type: application/pdf`. Зеркало на uni-erlangen (которое мы
  использовали для `jornada720.txt`) содержит тот же документ, но
  обрезанный до 19 страниц (только Introduction, до карты регистров не
  доходит).
- `raw.githubusercontent.com` и `codebrowser.dev` **не открываются с
  телефона** — TLS-соединение обрывается сразу после ClientHello, похоже
  на блокировку по SNI на уровне сети/провайдера. Обход: те же файлы
  GitHub доступны через CDN-зеркало **jsdelivr**
  (`cdn.jsdelivr.net/gh/<org>/<repo>@<tag>/<path>`), которое не
  заблокировано и отдаёт identичный контент.

**Уточнение регистровой карты SA-1111 (через реальные исходники Linux,
не через сам даташит):**
- `arch/arm/include/asm/hardware/sa1111.h` даёт базы блоков: SBI(`0x0`),
  System Controller/SKPCR(`0x200`), USB(`0x400`), Serial Audio(`0x600`,
  под-регистры `0x00-0x80`), GPIO(`0x1000`, под-регистры `0x000-0x02c`),
  Interrupt Controller(`0x1600`, под-регистры `0x0000-0x0038`),
  PS/2 KBD(`0xa00`), PS/2 MSE(`0xc00`). **Важно:** в этом заголовке
  `SA1111_PCMCIA` тоже указан как `0x1600` — это ошибка/пережиток
  (совпадает с INTC), реальную PCMCIA-базу он не даёт.
- `drivers/usb/host/ohci-sa1111.c` даёт точные вендорские регистры USB:
  `USB_STATUS=0x0118`, `USB_RESET=0x011c`, `USB_IRQTEST=0x0120`
  (относительно базы `0x400` → абсолютные `0x518/0x51c/0x520`). Это
  **опровергло** более раннюю гипотезу, что зависание на `0x810`
  связано с USB.
- `arch/arm/common/sa1111.c` (реальная таблица устройств чипа) даёт
  настоящие базы блоков, которых нет в упрощённом заголовке:
  **SSP = `0x0800`**, **PCMCIA = `0x1800`** (совпало с тем, что мы
  реально видели в трассировке — обращения к `0x1800`/`0x1808`!).
  Значит `0x40000810` = SSP-база (`0x800`) + смещение `0x10` —
  почти наверняка **SSP Status Register**.

**Фикс (экспериментальный, не проверен по даташиту):** добавил в
`jornada720.c` отдельный небольшой `MemoryRegion` с кастомными `ops`
(наложен поверх общей SA-1111 unimplemented-заглушки с приоритетом
выше), который отвечает на чтения из диапазона SSP (`0x40000800`,
4 КиБ) фиксированным значением вместо генерируемого нуля:
- Первая попытка — `0xFFFFFFFF` (все биты) — сняла зависание на `0x810`,
  но тут же поймали **второй** бесконечный цикл (тихий, без unimp-лога,
  видно только по `-d in_asm`: PC топчется в районе `0x500cc-0x501e8`).
  Вывод: код ждёт не только "бит готовности = 1", но где-то и "бит
  занятости = 0" в том же регистре — все единицы одновременно ломают
  обе проверки.
- Взял по аналогии битовую раскладку **on-chip SA-1110 SSP**
  (`strongarm_ssp` в `hw/arm/strongarm.c`, тот же IP-блок скорее всего
  переиспользован и в SA-1111): `TNF=бит2, RNE=бит3, TFS=бит5, RFS=бит6,
  ROR=бит7(чисто)` → отдаю `(1<<2)|(1<<3)|(1<<5)|(1<<6) = 0x6C`.
  **Сработало** — второй цикл тоже пройден.

**Результат:** исполнение доходит до инициализации **Epson-контроллера
дисплея** — полностью **обнуляет весь framebuffer** (все 512 КиБ,
слово за словом, ровно 0x20000 записей — сошлось день в день с
`J720_EPSON_FB_SIZE`), затем пишет `0x01` в Epson-регистр по смещению
`0x1fc` (1 байт) — и **детерминированно зависает** сразу после этого
(проверено дважды, останавливается на одной и той же строке лога).
Serial-консоль всё ещё молчит.

**Текущий стопор (next task):** нужно (а) определить точную модель
Epson-чипа на Jornada 720 (в TOC даташита он не упоминается вовсе —
подключён как отдельный вендорский чип, не часть SA-1111/SA-1110;
кандидаты — семейство Epson SED13xx, но конкретная модель не
подтверждена) и (б) понять, что означает регистр `0x1fc` и какой статус
код ждёт после записи в него (тот же паттерн "запись конфига → опрос
готовности", что и с SSP). У QEMU для Epson-чипов вообще нет ни одной
реализации ни для одной модели SED13xx, так что тут придётся либо
искать датащит конкретной модели, либо реализовывать с нуля по
догадкам/сверке с MAME.
