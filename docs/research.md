# Research / собранные факты

## Железо HP Jornada 720/728

- CPU: **Intel StrongARM SA-1110**, 206 МГц (не SH3 — SH3 стоит в других
  линейках Jornada, например 680/690 и 520/540).
- ОС: Windows CE (Handheld PC 2000, на 720/728).
- Подробная распиновка/карта регистров: см. hardware config doc
  (jornada720.txt, из архива уровня "hpc factor" / университетских зеркал) —
  описывает маппинг SA1110 serial port, GPIO, control registers и т.п.
  Это и есть основа для memory map будущей QEMU-машины.

## Прецедент в MAME

- Файл `src/mame/**/jornada.cpp` — драйвер именно HP Jornada 720/728.
- Использует отдельный, переиспользуемый файл эмуляции чипа `sa1110.cpp`
  (аналог `hw/arm/strongarm.c` в QEMU).
- Автор основной работы — **Ryan Holtz**.
- Результат: Windows CE грузится "до узнаваемого состояния" (виден UI).
- Известные проблемы:
  - нужно запускать с флагом `-debug` и вручную подкручивать скорость CPU
    через cheat-параметры отладчика, иначе не бутится нормально;
  - тачскрин работает нестабильно/криво;
  - даже на десктопном **Intel i5-4670K** эмуляция описывается как
    "очень медленная", загрузка до рабочего стола — "целая вечность".
- PR с доработкой клавиатурной раскладки смержен в mamedev/mame в январе 2024 —
  то есть проект живой, но статус экспериментальный, не production-ready.
- Значение для нас: подтверждает, что задача **решаема** (SA-1110 достаточно
  эмулируется программно, чтобы Windows CE стартовала), и даёт готовый
  referencing-таргет — можно сверяться с логикой jornada.cpp/sa1110.cpp при
  написании аналога под QEMU.

## Состояние в QEMU

- Готовой машины для Jornada (ни 56x/SA-1110, ни 6xx/7xx на SH3) в апстриме нет.
- Поиск по GitHub / qemu-devel / mail-archive не дал патчей или форков с
  поддержкой Jornada — похоже, что до сих пор никто не выкладывал такую работу
  в открытом виде.
- **`hw/arm/strongarm.c`** (+ `strongarm.h`) — эмуляция чипа SA-1110, но
  она **неполная** (см. разбор ниже) — не стоит переоценивать, сколько
  "готового" там есть.
- Её использует машина **`hw/arm/collie.c`** — Sharp Zaurus SL-5500,
  тоже построен на SA-1110. Основной шаблон/референс для платы.

### Разбор `hw/arm/strongarm.c` — что реально уже есть (128 KiB, 1671 строка)

`sa1110_init()` (главная точка входа, `strongarm.h`) поднимает:

| Периферия | Адрес      | Реализация |
|---|---|---|
| PIC (контроллер прерываний) | `0x90050000` | `strongarm_pic` |
| OS-таймер | `0x90000000` | переиспользован `pxa25x-timer` (не своя модель!) |
| RTC | `0x90010000` | `strongarm-rtc` |
| GPIO | `0x90040000` | `strongarm-gpio` |
| PPC (Peripheral Pin Controller) | `0x90060000` | `strongarm-ppc` |
| UART x3 | `0x80010000` / `0x80030000` / `0x80050000` | `strongarm-uart` |
| SSP (синхронный serial/SPI, обычно touchscreen ADC / кодек) | `0x80070000` | `strongarm-ssp`, с выведенной наружу SSI-шиной |

**Чего в strongarm.c НЕТ** (моя более ранняя запись в этом файле была
неточной — ошибочно предполагала, что LCD/DMA/PCMCIA уже есть):

- **LCD-контроллер — отсутствует полностью.** У SA-1110 в реальности есть
  встроенный LCD-контроллер, но в QEMU его никто не реализовал. Машина
  `collie` тоже не подключает никакого экрана — то есть на сегодня в QEMU
  **нет вообще ни одной SA-1110-платы с рабочим видеовыходом**.
- DMA-контроллер — не реализован как устройство (хотя в PIC заведены
  IRQ-линии `SA_PIC_DMA_CH0..5` под него — заготовка есть, самого блока нет).
- PCMCIA-контроллер — тоже не часть strongarm.c. У `collie` вместо этого
  подключен Sharp-специфичный `scoop` (0x40800000) — то есть это
  Zaurus-специфика, для Jornada неприменимо один в один.
- Флеш подключается на уровне платы (`collie.c`), не чипа — это ожидаемо
  и одинаково для любой SA-1110 платы, в т.ч. будущей Jornada.

**Вывод (скорректированный):** писать модель CPU-ядра и базовых
блоков (PIC/таймер/RTC/GPIO/UART/SSP) с нуля не требуется — это есть и
переиспользуется 1:1, адреса общие для любого SA-1110-чипа, в т.ч. Jornada 720.
Но **экран — не "мелкая доработка", а отдельная, довольно большая
задача**: LCD-контроллер SA-1110 в QEMU нужно писать с нуля (в MAME он,
судя по всему, есть — раз там видно UI — значит это одна из вещей, которую
стоит внимательно сверить по их `sa1110.cpp`, а не только по железным
даташитам).

Отсюда практический вывод для плана: реалистичная первая цель — это
именно **шаг 1 (загрузка до UART-консоли, без экрана)**, он полностью
укладывается в то, что уже есть в strongarm.c. Шаг 2 (экран) по объёму
работы сопоставим с написанием ещё одного устройства с нуля, а не с
"передать конфиг панели в готовый контроллер", как было наивно записано
здесь раньше.

## Карта памяти Jornada 720 (из hardware config doc, jornada720.txt)

| Регион | Адрес | Размер | Статус в нашей машине |
|---|---|---|---|
| System Flash/ROM | `0x00000000` | 32 MiB | подключен (`SA_CS0`, `pflash_cfi01`) |
| Boot Flash/ROM (только debug-плата) | `0x10000000` | 1 MiB | не нужен, это для отладочной платы, не для обычного устройства |
| SA-1111 companion chip | `0x40000000` | — | НЕ эмулируется, совпадает с `SA_CS4` |
| Epson-контроллер дисплея | `0x48000000` | — | НЕ эмулируется |
| Epson frame buffer | `0x48200000` | 512 KiB | НЕ эмулируется |
| System SDRAM | `0xC0000000` | 32 MiB | подключен (`SA_SDCS0`) |

Важное уточнение по экрану: у Jornada 720 дисплей выведен не через
встроенный в SA-1110 LCD-контроллер, а через **отдельный Epson-чип**
(похоже на семейство Epson SED13xx — точная модель ещё не подтверждена).
Проверил исходники QEMU (`grep -rli` по `hw/` и `include/`) — **ни SA-1111,
ни какого-либо Epson SED13xx контроллера в QEMU нет вообще**. Значит шаг
"экран" требует написания не одного, а потенциально **двух** устройств
(SA-1111 — если он нужен раньше экрана, например для клавиатуры/USB;
Epson-контроллер — для самого видео). Нужно уточнить по MAME `sa1110.cpp`/
`jornada.cpp`, что из этого они реализовали и в каком объёме.

## Прогон реального ROM (2026-09-28)

Пользователь поднял у себя дома веб-сервер и передал реальные дампы с
Jornada 720: `jornada720.bin` (ровно 32 МиБ — точно system flash) и
`jorn720_eeprom.bin` (256 байт, пока не использован). Файлы лежат в
`roms/` (не в git, см. `.gitignore`).

Загрузка (`-drive if=pflash,format=raw,file=roms/jornada720.bin`) сразу
показала: **тишина в serial-консоли** — так что пришлось отлаживаться
через `-d in_asm`/`-d unimp`/`-d guest_errors` и временную инверсию
`mc->ignore_memory_transaction_failures`, чтобы понять, где именно
исполнение застревает. Разбор по шагам:

1. **Сброс → `0x00000000` → branch на `0x00001000`** — стандартный
   ARM-паттерн (короткий вектор сброса прыгает на реальный код). ОК.
2. С `0x1000` до `~0x107c` код несколько раз пишет в **`cp15, c1, c1, opc2=0`**
   (не крн=15 "impdef", а именно `c1,c1`) — QEMU логировал это как
   `unsupported AArch32 system register` и **бросал Undefined Instruction**.
   На реальном железе это легитимный (хоть и слабо документированный)
   SA-1110-специфичный "Auxiliary Control Register", который просто должен
   тихо срабатывать. Так как вектор Undefined Instruction (`0x00000004`)
   в этом ROM пуст (`0xFFFFFFFF`), исключение зацикливалось само на себя —
   полное зависание уже на первых ~30 инструкциях.
   **Фикс:** добавил RAZ/WI-запись в `strongarm_cp_reginfo`
   (`target/arm/helper.c`, по аналогии с уже существующим `C9_READBUFFER`) —
   см. `patches/0002-sa1110-aux-control-register-dummy.patch`.
3. После фикса исполнение уходит гораздо дальше (`0x4f7xx`-`0x505xx`),
   делает что-то похожее на калиброванный **delay-loop** через запись
   нарастающего счётчика в регистр отладочной платы (CL-CD1284,
   `0x1a000400`) — это ожидаемо и не мешает (на реальном железе без
   debug-платы это обращение просто читает "мусор" с шины, а не падает;
   поэтому `ignore_memory_transaction_failures` должен остаться `true`,
   как у `collie.c` — я на секунду включал `false` только для диагностики
   через Data Abort, там и увидел `DFAR 0x1a000400`, что и навело на след).
4. Дальше код инициализирует **SA-1111** (пишет в блоки по смещениям
   `0x0000`, `0x0004`, `0x1000-0x102c`, `0x1608-0x1620` — похоже на
   System Bus Interface / PCMCIA / GPIO блоки) и в итоге **зависает
   намертво в бесконечном read-poll по смещению `0x000810`** от базы
   SA-1111 (`0x40000810`). Заглушка (`create_unimplemented_device`)
   всегда отдаёт 0, а код явно ждёт другого значения бита — реальный
   SA-1111 в этот момент отвечает чем-то, что делает проверку истинной.
   За 15 секунд — больше 2 млн одинаковых чтений одного и того же адреса.

Добавлены read/write-заглушки (`hw/misc/unimp.h` →
`create_unimplemented_device`) на все ещё не эмулированные регионы —
SA-1111 (`0x40000000`), debug-плата (`0x1a000000`), Epson-регистры
(`0x48000000`) и Epson-framebuffer (`0x48200000`) — чтобы дальнейшие
обращения были видны через `-d unimp`, а не тонули в тишине.

## Раскопка даташита SA-1111 и разгон стопора на `0x810` (2026-09-28, продолжение)

**Проблемы с источниками:**
- Полный "Developer's Manual" (278242-002) на bitsavers.org оказался
  **битым** — под этим именем лежит старая dead-link HTML-страница
  Intel (~2000 год), просто сохранённая с расширением `.pdf` и
  `Content-Type: application/pdf`. Зеркало на uni-erlangen (которое мы
  использовали для `jornada720.txt`) содержит тот же документ, но
  обрезанный до 19 страниц (только Introduction, до карты регистров не
  доходит).
- `raw.githubusercontent.com` и `codebrowser.dev` **не открываются с
  телефона** — TLS-соединение обрывается сразу после ClientHello, похоже
  на блокировку по SNI на уровне сети/провайдера. Обход: те же файлы
  GitHub доступны через CDN-зеркало **jsdelivr**
  (`cdn.jsdelivr.net/gh/<org>/<repo>@<tag>/<path>`), которое не
  заблокировано и отдаёт identичный контент.

**Уточнение регистровой карты SA-1111 (через реальные исходники Linux,
не через сам даташит):**
- `arch/arm/include/asm/hardware/sa1111.h` даёт базы блоков: SBI(`0x0`),
  System Controller/SKPCR(`0x200`), USB(`0x400`), Serial Audio(`0x600`,
  под-регистры `0x00-0x80`), GPIO(`0x1000`, под-регистры `0x000-0x02c`),
  Interrupt Controller(`0x1600`, под-регистры `0x0000-0x0038`),
  PS/2 KBD(`0xa00`), PS/2 MSE(`0xc00`). **Важно:** в этом заголовке
  `SA1111_PCMCIA` тоже указан как `0x1600` — это ошибка/пережиток
  (совпадает с INTC), реальную PCMCIA-базу он не даёт.
- `drivers/usb/host/ohci-sa1111.c` даёт точные вендорские регистры USB:
  `USB_STATUS=0x0118`, `USB_RESET=0x011c`, `USB_IRQTEST=0x0120`
  (относительно базы `0x400` → абсолютные `0x518/0x51c/0x520`). Это
  **опровергло** более раннюю гипотезу, что зависание на `0x810`
  связано с USB.
- `arch/arm/common/sa1111.c` (реальная таблица устройств чипа) даёт
  настоящие базы блоков, которых нет в упрощённом заголовке:
  **SSP = `0x0800`**, **PCMCIA = `0x1800`** (совпало с тем, что мы
  реально видели в трассировке — обращения к `0x1800`/`0x1808`!).
  Значит `0x40000810` = SSP-база (`0x800`) + смещение `0x10` —
  почти наверняка **SSP Status Register**.

**Фикс (экспериментальный, не проверен по даташиту):** добавил в
`jornada720.c` отдельный небольшой `MemoryRegion` с кастомными `ops`
(наложен поверх общей SA-1111 unimplemented-заглушки с приоритетом
выше), который отвечает на чтения из диапазона SSP (`0x40000800`,
4 КиБ) фиксированным значением вместо генерируемого нуля:
- Первая попытка — `0xFFFFFFFF` (все биты) — сняла зависание на `0x810`,
  но тут же поймали **второй** бесконечный цикл (тихий, без unimp-лога,
  видно только по `-d in_asm`: PC топчется в районе `0x500cc-0x501e8`).
  Вывод: код ждёт не только "бит готовности = 1", но где-то и "бит
  занятости = 0" в том же регистре — все единицы одновременно ломают
  обе проверки.
- Взял по аналогии битовую раскладку **on-chip SA-1110 SSP**
  (`strongarm_ssp` в `hw/arm/strongarm.c`, тот же IP-блок скорее всего
  переиспользован и в SA-1111): `TNF=бит2, RNE=бит3, TFS=бит5, RFS=бит6,
  ROR=бит7(чисто)` → отдаю `(1<<2)|(1<<3)|(1<<5)|(1<<6) = 0x6C`.
  **Сработало** — второй цикл тоже пройден.

**Результат:** исполнение доходит до инициализации **Epson-контроллера
дисплея** — полностью **обнуляет весь framebuffer** (все 512 КиБ,
слово за словом, ровно 0x20000 записей — сошлось день в день с
`J720_EPSON_FB_SIZE`), затем пишет `0x01` в Epson-регистр по смещению
`0x1fc` (1 байт) — и **детерминированно зависает** сразу после этого
(проверено дважды, останавливается на одной и той же строке лога).
Serial-консоль всё ещё молчит.

**Текущий стопор (next task):** нужно (а) определить точную модель
Epson-чипа на Jornada 720 (в TOC даташита он не упоминается вовсе —
подключён как отдельный вендорский чип, не часть SA-1111/SA-1110;
кандидаты — семейство Epson SED13xx, но конкретная модель не
подтверждена) и (б) понять, что означает регистр `0x1fc` и какой статус
код ждёт после записи в него (тот же паттерн "запись конфига → опрос
готовности", что и с SSP). У QEMU для Epson-чипов вообще нет ни одной
реализации ни для одной модели SED13xx, так что тут придётся либо
искать датащит конкретной модели, либо реализовывать с нуля по
догадкам/сверке с MAME.

## Настоящая причина зависания на Epson `0x1fc`: баг в битах SSSR у QEMU (2026-09-28, продолжение 2)

Оказалось, что зависание после записи `0x1fc` было вовсе не про Epson —
это был поход через **on-chip SA-1110 SSP** (реальное, давно
существующее устройство `strongarm.c`, не наша заглушка), используемый
как SPI-канал к Epson-чипу (с chip-select через GPIO).

**Как нашли:** поставили `gdb` (`doas apk add gdb`, пользователь
установил вручную), остановили QEMU через monitor (`stop` +
`info registers`) прямо в момент зависания — `PC=0x0004f26c`,
`R04=0x80070074` (SSSR), `R05=0x8007006c` (SSDR), `R06=0x90040000`
(GPIO). Встроенный дизассемблер монитора не поддерживает ARM
(`Asm output not supported on this arch`), так что дизассемблировали сам
ROM через `objdump -D -b binary -m arm --adjust-vma=0x0
--start-address=... --stop-address=...` — `objdump` на aarch64-хосте
прекрасно умеет 32-битный ARM.

Дизассемблированный код чётко показал два poll-цикла на SSSR:
- `ands r3,r3,#4` (бит2) — "слить" цикл: входит если бит2=1, крутится
  пока бит2=1, выходит когда бит2=0.
- `ands r3,r3,#2` (бит1) — противоположный: крутится пока бит1=0, выходит
  когда бит1=1.

Сверили с существующими (не нашими) `#define` в `hw/arm/strongarm.c`:
`SSSR_TNF=бит2, SSSR_RNE=бит3, SSSR_TFS=бит5, SSSR_RFS=бит6, SSSR_ROR=бит7`
— то есть эмулируемый TNF (бит2) **жёстко всегда 1**, пока SSP включён
(см. `strongarm_ssp_fifo_update`: `/* TX FIFO is never filled, so it is
always in underrun condition if SSP is enabled */`). При повторном
вызове этой процедуры (SSP уже включён с прошлого раза) цикл "крутится
пока бит2=1" **не может завершиться никогда** — независимо от того, что
подключено к SSI-шине.

**Настоящая причина оказалась глубже:** позиции битов в `strongarm.c`
скопированы из PXA25x-модели SSP и **не совпадают с реальным SA-1110**.
Скачали официальный **SA-1110 Developer's Manual**
(`278240-003_SA-1110_Developers_Manual_200006.pdf`, bitsavers.org — в
отличие от SA-1111-мануала, этот оказался нормальным, не битым PDF) и
нашли раздел 11.12.12 (SSSR): **бит1=TNF, бит2=RNE, бит3=BSY, бит4=TFS,
бит5=RFS, бит6=ROR** — то есть все биты сдвинуты на 1 позицию ниже
относительно того, что было в QEMU.

С реальной раскладкой оба цикла из ROM внезапно обретают смысл:
- Цикл на бите2 = **RNE** (Receive Not Empty) — "слить оставшиеся байты
  из прошлого приёма перед новой передачей", входит если RNE=1, выходит
  когда RNE=0. Полностью корректный, завершающийся цикл.
- Цикл на бите1 = **TNF** (Transmit Not Full) — "ждать места в очереди
  на передачу", выходит когда TNF=1 (что в модели QEMU и так почти
  всегда true).

**Фикс:** поправили позиции битов в `hw/arm/strongarm.c` на настоящие
(`SSSR_TNF=1<<1, RNE=1<<2, добавлен BSY=1<<3 (не используется, но для
полноты), TFS=1<<4, RFS=1<<5, ROR=1<<6`, `SSSR_RW` тоже пересчитан под
новую позицию ROR). Это правка **уже существующего, не нашего кода**
QEMU, используемого и другими платами (`collie`) — теоретически более
правильная для всех SA-1110-машин, не только Jornada 720, но не
проверялась на предмет регрессий для `collie`.

**Результат:** зависание снято. Загрузка пошла ЗНАЧИТЕЛЬНО дальше —
теперь реально **рисует во framebuffer** (запись `0xFFFF`, 16 бит/пиксель,
белый цвет, широким диапазоном адресов — похоже на отрисовку сплэш-экрана
или фона UI), причём объём операций вырос с 131214 до 285204 строк
unimp-лога. Debug-board delay-loop продолжается как обычно.

**Новый стопор:** после этого — **настоящий Data Abort**
(`PC=0xffff0010` — это Data Abort вектор в **высокой** таблице векторов
`0xFFFF0000`, то есть V-бит CP15 к этому моменту уже включён; режим
CPU — `abt32`). `LR_abt=0x800558cc` — это уже НЕ адрес во флеше, а
что-то в районе on-chip peripheral-пространства/RAM — то есть к этому
моменту код уже **релоцировал себя в RAM** и исполняется оттуда, что
делает дальнейшую отладку через статичный `objdump` по файлу ROM
неприменимой напрямую (нужно читать память самой VM в момент
зависания, не статический файл). Serial-консоль всё ещё молчит.

Это уже принципиально другой класс задачи (не "добавить заглушку
периферии", а разобраться в чём-то на уровне релоцированного кода/MMU) —
хорошая точка для передышки или для отдельного захода с прицелом именно
на это.

## Найдена настоящая первопричина: MMU-enable без "зазора" в QEMU (2026-09-28, продолжение 3)

Отладка через QEMU gdbstub (`-s -S`, `target remote :1234`), с ключевым
уроком: **detach в gdb по умолчанию делает resume** — если между
установкой breakpoint'а и `continue` был отдельный detach/reconnect,
код успевает свободно убежать вперёд, и следующий breakpoint ловит уже
не первое, а какое-то из последующих срабатываний. Нужна **одна
непрерывная gdb-сессия** от `target remote` до нужного breakpoint'а.

Также полезно: `pkill -f qemu-system-arm` матчит **всю командную
строку** процесса, включая наш же управляющий скрипт (если он текстом
содержит "qemu-system-arm" — например, в следующей же строке скрипта,
где мы его перезапускаем) — рискует убить сам себя раньше, чем дойдёт
до перезапуска. `pkill -x` (точное имя `comm`) надёжнее, но в одном
случае тоже не сработал необъяснимо — если попадается, надёжнее просто
`kill -9 <конкретный PID>` из `ps ax`.

**Ход расследования:** поставили breakpoint не только на векторе Data
Abort (`0xffff0010`), но сразу на всех шести (`0xffff0004/0008/000c/
0010/0018/001c`) и продолжили с самого начала (PC=0) одной сессией.
Сработал **не Data Abort, а Prefetch Abort** (`0xffff000c`) —
предыдущие находки про Data Abort были уже вторичным следствием.

Регистры на этом breakpoint: `LR=0x000555f4` (упавшая инструкция —
`LR-4=0x555f0`), `IFSR=0x5` (Translation fault, Section), `SCTLR=0x327f`
(бит0 M=1 — **MMU уже включён**), `TTBR0=0xc0020000`.

Прочитали таблицу страниц напрямую из физической памяти через
`monitor xp/8xw <addr>` в gdb (обычный `x` в gdb идёт через **текущую**
трансляцию гостя и сам фолтится на том же адресе — that's expected,
подтверждает, что адрес правда не замаплен):
- Индекс для VA `0x00000000` (наш `0x555f0`): **всё нули** — fault-дескриптор,
  ничего не замаплено.
- Индекс для VA `0x80000000`+: замаплено **корректными** section-дескрипторами
  на PA `0x00000000`, `0x00100000`, `0x00200000`, `0x00300000` — то есть
  ROM замаплен только по высокому алиасу (`+0x80000000`), низкий алиас
  (тот, откуда физически исполняется код прямо сейчас) не замаплен вовсе.

Дизассемблировали ROM статически (`objdump -D -b binary -m arm`) вокруг
`0x555e0`:
```
555d8: mrc 15,0,r1,cr1,cr0,{0}      ; читаем SCTLR
555dc: orr r1,r1,#0x7f
555e0: orr r1,r1,#0x3200            ; V(hivecs)=1, I(icache)=1, ...
555e4: ldr r0,[pc,#124]  -> 0x800555f8   ; целевой адрес = высокий алиас
555e8: cmp r0,#0
555ec: mcr 15,0,r1,cr1,cr0,{0}      ; ЗАПИСЬ SCTLR: тут MMU включается (M=1)
555f0: mov pc,r0                    ; переход на высокий алиас
```

Это классическая ARM-идиома "MCR SCTLR(enable MMU) → следующая
инструкция — branch на тот же код через другой (уже замапленный)
алиас". Архитектурно ARM прямо называет поведение инструкций сразу
после такого MCR **unpredictable**, и общепринятая практика (в т.ч.
Linux `head.S`) — не полагаться на это, а явно делать identity-map
текущего физического адреса перед включением MMU. Судя по всему,
реальный SA-1110 в железе всё же гарантированно "дотягивает" именно
эту следующую инструкцию (`mov pc,r0` по адресу `0x555f0`) через старое
(ещё не транслируемое) отображение — иначе прошивка не грузилась бы ни
на одном реальном устройстве.

**В QEMU этого зазора нет**: судя по наблюдаемому поведению, запись в
SCTLR (смена M-бита) вступает в силу немедленно для *следующей же*
выборки инструкции — а `0x555f0` не замаплен ни в одной таблице, отсюда
мгновенный Prefetch Abort прямо на этой инструкции. Это, вероятно,
следствие того, как QEMU TCG завершает translation block при записи в
MMU-влияющие CP15-регистры (пересборка hflags/трансляции происходит
сразу, без "лишней" инструкции на старом отображении) — общее свойство
таргета `target/arm`, а не что-то специфичное для SA-1110/collie/нашей
машины.

**Открытый вопрос / следующий шаг:** нужно либо (а) найти существующий
механизм в `target/arm/helper.c` (запись SCTLR/`cp_reginfo` для c1),
дающий эту "отсрочку на одну инструкцию", и понять, можно ли безопасно
её добавить только для этого перехода (M: 0→1 одновременно с V: 0→1),
не ломая остальные ARM-машины; либо (б) поискать другой обходной путь
специфично для нашей `jornada720.c` (например, если возможно как-то
предзаполнить нужную запись таблицы страниц ДО того, как гостевой код
её прочитает — не очевидно, как это сделать чисто, таблицу строит сам
гость в RAM в рантайме). Это уже правка на уровне `target/arm`
(общий ARM CPU core QEMU), не `hw/arm/jornada720.c` — по масштабу
сопоставимо с прошлыми фиксами (aux control register, SSSR bits), но
глубже, так как трогает механизм трансляции инструкций, а не просто
чтение/запись одного регистра.

## Фикс варианта (а): ARM_CP_SUPPRESS_TB_END на SCTLR для strongarm (2026-09-28, продолжение 4)

Нашли готовый механизм в самом QEMU: `target/arm/tcg/translate.c` —
после записи в любой cp15-регистр по умолчанию форсируется конец
translation block + пересборка hflags (`gen_rebuild_hflags` +
`gen_lookup_tb`), **если** только у регистра не выставлен флаг
`ARM_CP_SUPPRESS_TB_END` (`target/arm/cpregs.h`, "usually only necessary
to work around guest bugs" — то есть механизм существует именно для
таких случаев). В проекте уже был прецедент точечного per-CPU
переопределения cp15-регистра именно для strongarm
(`strongarm_cp_reginfo` в `target/arm/helper.c`, `ARM_FEATURE_STRONGARM`
— используется только `sa1100`/`sa1110`, т.е. только `collie` и нашей
машиной, больше нигде).

Патч (`target/arm/helper.c`, в generic-блоке регистрации SCTLR_EL1):
после сборки структуры `sctlr` перед `define_one_arm_cp_reg` добавлена
проверка `if (arm_feature(env, ARM_FEATURE_STRONGARM))
sctlr.type |= ARM_CP_SUPPRESS_TB_END;`. Это позволяет инструкции сразу
после `mcr` (в нашем случае — `mov pc,r0`, переход на высокий алиас)
доисполниться в рамках уже скомпилированного TCG-блока по старому
(до записи) отображению, вместо немедленного форс-выхода — то есть
воспроизводит именно то поведение реального железа, на которое
рассчитывает ROM. **Не проверялось на регрессии для `collie`/других
strongarm-гостей** (тот же риск, что и у более раннего фикса битов
SSSR).

Пересобрали, прогнали без `-S`: `-d unimp` лог вырос с "зависает почти
сразу" до нескольких миллионов строк за 15 секунд и появилась новая,
ранее недостижимая активность (`debugboard` offset `0x13c`/`0x400`) —
переход на высокий алиас и вход в настоящее ядро WinCE наконец
происходит.

## Второй стопор после фикса MMU: SA-1110 Power Manager (POSR), не реализован в strongarm.c

После MMU-фикса лог стабильно останавливался на одном и том же числе
строк (детерминированно) — не через unimp-заглушку, а полностью
молча: процесс живёт (растёт CPU time), но `-d unimp` больше ничего не
пишет. Через gdbstub (одна непрерывная сессия, `interrupt` вместо
breakpoint, т.к. процесс не был на паузе) поймали PC в цикле из 4
инструкций (`ldr r3,[r4]; sub r3,r3,r5; cmp r3,r0; bcc` назад) —
классический busy-wait "жди N тиков аппаратного счётчика". Сравнение
двух снятий с разницей ~20 секунд реального времени показало, что
`r5` ("стартовый" снимок счётчика) каждый раз новый — то есть это не
один зависший вызов, а функция задержки (нашли её пролог:
`push {r4,r5,lr}` на `0x80076f98`, множитель `0x9000`=36864 ≈ тики
3.6864 МГц — классический `OALStall`/задержка-в-микросекундах)
вызывается заново внешним циклом.

Прочитали адрес возврата из стека (`[sp+8]`, сохранённый прологом) —
внешний цикл на `0x80077318`: делает **два** вызова
`OALStall(100000 мкс)` подряд (итого 200 мс), затем проверяет бит 0
слова по адресу `*(*(r6)+28)`, если 0 — снова 200 мс ожидания и по
кругу, если 1 — идёт дальше.

`*r6` во время проверки = `0xa3420000` (виртуальный "uncached"-алиас,
конвенция WinCE `0xA0000000+`). Прочитали L1-дескриптор через
`monitor xp` (physical, в обход MMU) — секция `0xa3400000`+ маппится на
физический `0x90000000`, то есть проверяемый адрес = физически
`0x90000000 + 0x20000 + 0x1c = 0x9002001c`.

`grep` по `hw/arm/strongarm.c`/`strongarm.h` на "power"/"PMCR"/"POSR" —
**ничего**: SA-1110 Power Manager блок (`0x90020000`, между RTC на
`0x90010000` и GPIO на `0x90040000`) в QEMU не реализован вообще.
Смещение `0x1c` в реальной карте регистров SA-1110 Power Manager —
это **POSR** (Oscillator Status Register), бит0 = "3.6864 МГц осциллятор
стабилен". На реальном железе выставляется вскоре после сброса; у нас
никогда не выставлялся → бесконечный retry.

**Фикс** (`src/hw/arm/jornada720.c`, тот же паттерн, что и SA-1111
SSP-стаб): `create_unimplemented_device` на весь блок `0x90020000`
(4 КиБ, для видимости будущих обращений через `-d unimp`) +
узкий 4-байтовый overlay ровно на `0x9002001c` (POSR), всегда
возвращающий бит0=1. Остальные регистры блока (PMCR/PSSR/PSPR/...)
пока не реализованы — если понадобятся, будет видно по логам.

**Результат:** оба фикса вместе продвинули загрузку значительно дальше
— в код с уже нормально проинициализированным `SP_abt` (`0xffff5000`,
не `0` как раньше).

## Третий стопор: Data Abort на записи в 0xffff5070 (после обоих фиксов)

Новый, не связанный с прошлыми, Data Abort: `LR=0x800558b8`,
упавшая инструкция (`LR-8=0x800558b0`) — `stm r0,{r4-r12,sp,lr}`,
классический пролог сохранения контекста при входе в обработчик
исключения (дамп регистров текущего режима в память по адресу в r0),
затем `msr CPSR_c,#0xd3` (переключение в SVC) и `b 0x80055818`.
`DFAR=r0=0xffff5070`, `DFSR=7` (Translation fault, Page).

`0xffff5070` — это тот же мегабайт (`0xFFF00000-0xFFFFFFFF`), что и
таблица векторов (`0xFFFF0000`), но другая 4-КиБ страница (+0x5000).
Таблица для этого мегабайта — **coarse** (L1-дескриптор
`0xc0029c01`, биты[1:0]=01 → указатель на L2-таблицу по `0xc0029c00`,
не section). Прочитали конкретные L2-записи через `monitor xp`:
- Страница таблицы векторов (`VA 0xFFFF0000`, L2-индекс `0xF0`,
  адрес записи `0xc0029fc0`) = `0xc002800e` — **валидный** дескриптор
  small-page (замаплено).
- Наша страница (`VA 0xFFFF5000`, L2-индекс `0x55`, адрес записи
  `0xc0029d54`) = `0x00000000` — **не замаплено вообще**.

То есть ядро замапило страницу с таблицей векторов, но НЕ страницу на
32 КиБ выше, куда пытается писать context-save при входе в обработчик
исключения (похоже на что-то вроде WinCE `KDataStruct`/per-CPU
exception-context области в верхних 64 КиБ адресного пространства).
Не выяснено: должна ли эта страница быть замаплена раньше (баг в
последовательности инициализации, возможно из-за ещё одного пробела в
эмуляции — например, EEPROM `jorn720_eeprom.bin` с конфигом платы,
который до сих пор нигде не подключен к машине и не читается), или
это указывает на другую, ещё не найденную причину. Не расследовано
до конца — хорошая точка для продолжения в следующий раз.

## Третий стопор решён: QEMU делал UNDEF из NV-условия на ARMv4 (2026-09-28, продолжение 5)

Ключ — `-d int` вместо gdb (gdb-сессии с условными breakpoint'ами
оказались ненадёжны: `Cannot access memory` на `continue`, программные
breakpoint'ы на `0xffff00xx` до включения MMU не ставятся — нужен
`hbreak`). В логе исключений перед первым abort'ом на `0xffff5070`
видна цепочка **Prefetch Abort → сразу Undefined Instruction** (единственный
UNDEF за весь прогон) → abort на `0xffff5070` в цикле.

Разбор (gdb, `hbreak` на вектор UNDEF и на `0x800557d0`):
- К этому моменту WinCE уже далеко: работают пользовательские процессы
  (FCSE PID `0x06000000`, слот 3), десятки тысяч Data/Prefetch Abort'ов —
  обычный demand paging.
- Упавший поток — ядро в `CallDLLEntry` (`0x80066f10`): `r4` = MODULE,
  `[r4+0x60]` = точка входа DLL (`0x00dbb4a8`), reason = 1
  (`DLL_PROCESS_ATTACH`). Страница кода DLL ещё не подкачана — Prefetch
  Abort штатный.
- Обработчик Prefetch Abort (`0x800557ac`) зовёт `LoadPageTable`
  (`0x80057420`); если не помогло, готовит `r1=3` и **проваливается**
  через два слова `0xf000fffc` и `0xffffc7fc` (второе — литерал!) в общий
  обработчик `0x800557f0`. Оба слова имеют условие **NV** (`cond=0xF`):
  на ARMv4/StrongARM это «никогда не выполнять», т.е. NOP, и код CE на
  это рассчитывает.
- QEMU (`target/arm/tcg/translate.c`, `disas_arm_insn`) для не-ARMv5
  трактует NV как UNPREDICTABLE и делает UNDEF. В результате общий
  обработчик вызывается из вектора UNDEF, где SPSR = abt (а не sys
  прерванного потока) → CE идёт по ветке «исключение внутри
  исключения» (`0x80055888`/`0x800558a8`): переключается в abt и
  сохраняет контекст по `sp_abt+0x70 = 0xffff5070` — выше стека abort'ов
  (`0xffff5000`), страница не замаплена → бесконечный Data Abort.

**Фикс** (`patches/0005-...`): для `ARM_FEATURE_STRONGARM` инструкция
с NV-условием — NOP. После него за 90 секунд прогона — ни одного UNDEF и
ни одного abort'а на `0xffff5070`; система продолжает работать
(IRQ, подкачка страниц, исполнение в пользовательском коде в районе
`0xf1xxxx`–`0xf3xxxx` текущего процесса, новых обращений к
незамапленной периферии в конце прогона нет). Что именно она делает —
без экрана не видно; Epson framebuffer у нас сейчас unimplemented-заглушка,
записи в него теряются. Регрессия для `collie` не проверялась.

Прошлая гипотеза про EEPROM `jorn720_eeprom.bin` не подтвердилась —
к этому стопору он отношения не имел.

## Экран: RAM-framebuffer + консоль 640x240 RGB565 — виден лого HP (2026-09-28, продолжение 6)

Заглушку `j720.epson-fb` (`0x48200000`, 512 КиБ) заменили на обычную RAM.
Поверх неё сделали графическую консоль QEMU: фиксированно 640x240,
RGB565, stride 1280, начало со смещения 0. Surface создаётся прямо из
RAM, без копирования. Регистры Epson при этом не декодируются, так что
start address / stride / bpp — догадка. Судя по картинке, верная: на
экране корректный лого **HP invent** (`docs/img/first-boot-logo.png`).

Как смотреть без GUI (в сборке есть только `none/curses/dbus` + VNC):
`-display none -monitor tcp:127.0.0.1:4444,server,nowait`, затем
`screendump file.ppm` через монитор, PPM → PNG самописным скриптом
(PIL нет). Unix-сокет для монитора не годится: путь scratchpad длиннее
108 байт.

**Что дальше не так:** кадр не меняется с 10-й по 90-ю секунду. К
регистрам Epson есть только разовая начальная инициализация (запись
таблицы в `0x80–0x8e`, `0x100–0x119`, `0x1e0–0x1fc`), дальше обращений
нет. CE при этом не простаивает: CPU крутится в пользовательском коде
(sys32), в основном `0x1b2ec–0x1b344` одного процесса (FCSE PID
`0x0c000000`) плюс DLL в районе `0x01faad00–0x01faae80` (вероятно
coredll), вперемешку с ядром. SA-1111: 808 чтений `0x60c` (блок audio,
вероятно SASR0) при инициализации звука, потом тишина.

**Грабли отладки:** ни gdb, ни `gva2gpa`, ни даже `-d in_asm` (пустое
дизассемблирование) не могут прочитать код пользовательских процессов:
L1-записи для этих слотов в таблице страниц (`TTBR0=0xc0020000`) нулевые,
хотя код исполняется. WinCE заполняет L1 лениво через `LoadPageTable` в
abort-обработчике и, видимо, очищает при переключении, а QEMU исполняет
по записям из своего softmmu-TLB. Проверили гипотезу «устаревший TLB из-за
FCSE»: `TLBIMVA` получает MVA с PID, а TLB QEMU индексирован по VA без
PID. Сделали полный flush при ненулевом FCSE — картинка не изменилась,
эксперимент откатили. Гипотеза не подтверждена, но и не опровергнута
полностью.

## Почему кадр застывал на лого: время в CE улетало из-за ISR таймера — лечится `-icount` (2026-09-28, продолжение 7)

**Кто крутится.** Статический разбор ROM: ROMHDR по VA `0x81666f4c`
(указатель лежит за сигнатурой `ECEC` по смещению `0x40`, ROM замаплен на
`0x80000000`), TOC — 218 модулей с e32/o32-заголовками. Код XIP-модулей
читается прямо из файла: `dataptr - 0x80000000`. Горячие адреса
`0x1b2ec`/`0x1b344` совпали с `explorer.exe`: это анимация

```
t0 = GetTickCount(); end = t0 + 200;      // или 350
while (GetTickCount() < end) { ...BitBlt... }
```

Через `hbreak *0x1b344` (фильтр по `$FCSEIDR == 0x0c000000`) увидели:
tick = 4692 мс и не растёт, хотя VM работает уже 40 с. Время ядра встало.

**Почему.** Регистры OST в этот момент: OSCR тикает, OSMR0 **позади**
счётчика, OIER=1, ICIP=0 — следующее совпадение будет только после
переполнения 32-битного счётчика (~19 мин при 3.6864 МГц). ISR таймера
в `nk.exe` (`0x80075638`, запись OSMR0 на `0x800756b4`):

```
OSSR = 1;
do { CurMSec++; ...; OSMR0 += 3686;       // 1 мс
     diff = OSMR0 - OSCR;                 // signed
} while (diff < 20 || diff > 3686);
```

Временный лог записей OSMR0 в `hw/timer/pxa2xx_timer.c` (после разбора
убран) показал цепочку. Догоняя отставание, ISR пишет OSMR0 = OSCR + 27
отсчётов (~7 мкс). В QEMU без icount OSCR идёт от часов хоста, а
эмулируемый CPU на телефоне сильно медленнее 206 МГц: пока ISR доходит до
чтения OSCR, 7 мкс проходят. Совпадение срабатывает внутри ISR
(прерывания запрещены), OSSR/IRQ взводятся, и после выхода ISR тут же
вызывается повторно — **раньше** следующего совпадения. Тогда
`diff > 3686`, и цикл крутится до обёртки 32-битного значения:
1 179 035 итераций в одном из прогонов, CurMSec улетает на ~19 минут,
дальше всё идёт вразнос. На реальном железе между записью и чтением
проходят наносекунды, так что это чисто эмуляционный эффект.

**Решение без правки кода:** `-icount shift=3,align=off` — виртуальное
время идёт от числа выполненных инструкций. Отрицательных дельт в ISR
больше нет; три больших значения OSMR0 пишет другой код (`0x80077ecc`,
похоже OEMIdle заводит длинный сон) — это легитимно. Итог: поверх лого
появились элементы рабочего стола — контур кнопки Start и трей с
батареей и часами «12:00 AM» (`docs/img/desktop-icount.png`).

**Что дальше не так:** после этого картинка не меняется, а виртуальное
время ползёт (~8 с виртуального за 3 мин реального). С icount это значит,
что CE непрерывно исполняет инструкции — где-то крутится. Не выяснено.

**Грабли:** `-d unimp` под icount пишет сотни МБ за минуту (миллионы
обращений к debug-плате, `0x13c`/`0x400`) и забил tmpfs `/tmp` (1.8 ГБ).
Для долгих прогонов логировать без `unimp`.
